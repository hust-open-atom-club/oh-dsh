# Agent Note: 侧边栏更新 rail 揭示折叠后才创建的入口

Status: implemented

[English](2026-09-06-sidebar-update-rail-late-reveal.md) | 中文

## 问题

桌面更新入口（[侧边栏更新入口 note](../feature/2026-09-04-sidebar-update-entry.md)）渲染两个 React 实例——logo 行内的宽控件与鲸鱼下方的 rail 控件——只有 frame 携带 `data-sidebar-collapsed` 时 rail 才显示。CSS 让折叠态 rail 按钮保持 `opacity: 0` 绘制，保证实时折叠提交时永远不会闪出图标。两条揭示路径都绑定在「按钮已存在」的瞬间：`onFold()` 在实时折叠期间添加滑入类，挂载路径则只能看到 React 已经渲染好的按钮。折叠之后才出现的入口——侧边栏保持折叠期间从 About 或更新窗口完成的更新检查——两条路径都匹配不上：React 只在 UI 状态离开 `hidden` 时创建按钮，而那时 `onFold()` 早已执行完毕，于是入口停在 CSS 的 `opacity: 0`，直到用户再次展开并折叠侧边栏。

## 决定

`mountEntry` 本来就在观察器每次看到 DOM 变更时重跑 `load()`，而每个 rail 按钮的诞生都是这样的变更。新增的 `revealRailEntry()` 在每次 `load()` 末尾运行：只要 frame 处于折叠态，就为尚未显示的 rail 按钮安排与实时折叠完全相同的一次性滑入——先清掉任何遗留的内联样式，保证入场永远从 CSS `opacity: 0` 基线开始，再按 `onFold()` 所用的 0 ms 计时器调度 `rail-enter` 类。该类的动画延迟加 `forwards` 填充会让按钮短暂隐藏、从 rail 右缘滑入一次并保持可见。揭示从不让入口先原地绘制，因此即使折叠正在进行，入场也不会被读成「先掉落再滑入」，也不会与实时折叠叠加——两边调度的是同一个类，而给已带类的元素再加同类是无操作。折叠态直接读 frame 属性而非 `prevCollapsed` 过渡追踪器，因此也覆盖「整个 frame 以折叠态挂载、该追踪器从未观察过折叠」的情形。原本有竞态的挂载时内联覆盖被删除；下一次实时折叠仍通过 `onFold()` 重启滑入——展开时它会清除该类，让每次折叠都能干净地重新入场。

## 曾考虑的替代方案

让迟到入口原地静态显示（第一版修复）：按钮瞬间弹入其行内，一旦实时折叠的滑入与该瞬间重叠，两个动作就会叠加——先原地出现、再横向滑入——且与其他 rail 行没有共享的入场语言。让折叠态 rail 在 CSS 中始终可见，则会取消保证折叠提交永不闪出图标的 `opacity: 0` 默认值。让揭示以 `prevCollapsed` 而非属性为准，会漏掉首个折叠记录之前诞生的入口——整个 frame 以折叠态挂载的情形。

## 后果

侧边栏已折叠时变为可用的入口现在恰好入场一次，使用其他 rail 控件在折叠时所用的同一条 railIn 动画——没有突兀的原地弹出，也没有任何东西能叠上第二个动画。揭示是幂等的，且只在实际 DOM 变更触发的 load 上运行，稳态零开销。冷/迟到挂载现在像折叠入口一样动画入场，而非静态显现：侧边栏已折叠时，图标在诞生约 150 ms 后从 rail 右缘滑入，而不是立即出现。
