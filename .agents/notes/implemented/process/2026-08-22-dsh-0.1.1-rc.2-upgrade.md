# Agent Note: Upgrade the pinned DSH runtime to 0.1.1-rc.2

Status: implemented

English | [中文](2026-08-22-dsh-0.1.1-rc.2-upgrade.zh.md)

## Problem

Oh-DSH pinned `@deepseek-ai/dsh@0.1.0-rc.7`. The upstream project
published `0.1.1-rc.2` (current `latest` tag), which changes three
contracts Oh-DSH consumes: the forwarded credential event was renamed,
the web client boot graph is injected under a different global marker,
and `dsh-client-ui-renderer` now owns `document.title` and rewrites it
to its own product title on view and session changes.

## Decision

- Re-pin `dsh-source.json` to `0.1.1-rc.2` (tarball plus SHA-512 from
  the npm registry) and regenerate
  `scripts/dsh-runtime-0.1.1-rc.2-lock.yaml` from the pristine release
  assembly's own resolution, deleting the rc.7 lockfile. The stage step
  still installs with `--frozen-lockfile`.
- Follow the released surface dependencies: dsh-TUI submodule → v0.8.8
  (which itself depends on the 0.1.1-rc.2 line), Better Sidebar
  submodule → v0.15.0, and the 13 `@deepseek-ai/dsh-*` dependencies in
  `plugins/vision/package.json` → `^0.1.1-rc.2`. Platform coverage is
  unchanged: staging resolves per-platform Node distributions for
  macOS arm64/x64, Linux x64, and Windows x64 from the same pin.
- Adapt the three contract changes at the narrowest seams:
  `credentials/updated` → `credentials/reference-updated` in the vision
  settings card; the smoke lanes read the boot graph from
  `globalThis["__DSH_BOOT__"]` instead of `window.__DSH_BOOT__`; the
  web shell keeps its title with a MutationObserver on
  `document.head` that reasserts `Oh-DSH Web` after each renderer
  rewrite, instead of racing a single assignment.
- `stage-dsh.mjs` stages the TUI's renamed `dsh-ecosystem-spec`
  directory under its new name; nothing else in the staging seam moved.

## Consequences

- The runtime lockfile name still derives from
  `DSH_SOURCE_SPEC.version`, so nix and CI pick up the new pin without
  hardcoded versions.
- The web title is now an ongoing assertion rather than a one-shot
  assignment; if DSH later exposes a product-title override, the
  observer should be replaced by that contract.
- Every `@deepseek-ai/dsh-*` resolution in the workspace now sits on
  `0.1.1-rc.2`. Two pnpm-workspace `overrides` hold the line where
  ranges alone drift: `dsh-working-activity`'s auto-installed
  optional peer re-resolves to the old `0.1.0-rc` line on a fresh
  install, and the pinned dsh-TUI submodule's `dsh-agent-instructions`
  range resolves nondeterministically. Never run `pnpm -r update` on
  this workspace: it rewrites `upstream/dsh-TUI/package.json` (the
  pinned submodule) and produces a lockfile CI's frozen install
  rejects. Re-resolve with targeted `pnpm update <packages>` and
  `pnpm dedupe` instead.

## Alternatives considered

- Keep rc.7 and only bump the submodules: dsh-TUI v0.8.8 requires the
  rc.2 package line, so the surfaces and the runtime would split;
  rejected.
- Override the renderer's title by patching its bundle in staging: the
  MutationObserver keeps the change in our own web client and survives
  upstream bundle hash changes; preferred.
