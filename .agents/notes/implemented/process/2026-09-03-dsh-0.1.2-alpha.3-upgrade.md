# Agent Note: Upgrade the pinned DSH runtime to the 0.1.2-alpha.3 line

Status: implemented

English | [中文](2026-09-03-dsh-0.1.2-alpha.3-upgrade.zh.md)

## Problem

The pinned runtime sat at `0.1.1-rc.2` (the npm `latest` tag). The 0.1.2
line moved four contracts Oh-DSH consumes: `@deepseek-ai/dsh-client-runtime`
is gone (the store engine moved to `dsh-client-store`, satisfied by the
shell kernel's static table like `cordis`), the slot system made session-
scoped child slots strict (a current-session provider must wrap the outlet),
the settings remote moved from `dsh-host-apiproxy` into
`dsh-api-settings-controller`, and the web server gates the UI behind a
launch-token exchange that mints a session cookie.

The newest release, `0.1.2-rc.1` (published 2026-09-03), removes the
`Session.events` getter from `dsh-session`. Every released dsh-TUI reads
`session.events` (channel/plugin/promptDebug), including v0.10.0-beta.4 and
its main branch — the TUI typecheck fails with ~50 TS2339 errors against
rc.1 and the property is gone at runtime. `0.1.2-alpha.2` (the TUI's own
validated line) is uninstallable: its assembly's devDependencies reference
three never-published `dsh-experimental-*` packages. alpha.4/alpha.5 also
removed `Session.events`.

## Decision

- Pin `0.1.2-alpha.3` — the newest installable release that dsh-TUI
  v0.10.0-beta.4 compiles and runs against (alpha.3 still ships
  `Session.events`; alpha.4 landed after beta.4 was cut). The rc.1 upgrade
  unblocks when dsh-TUI ships the Session-projection adaptation; the daily
  upstream watch keeps flagging newer releases.
- Follow the released surface dependencies: dsh-TUI submodule → v0.10.0-beta.4
  (nested dsh-auth → 4e7cba3 "support dsh 0.1.2-alpha.1", ecosystem-spec →
  d28c267), Better Sidebar → v0.18.0-alpha.0 (upstream's own "DSH
  0.1.2-alpha.x only" release; v0.17.1 still imports the removed
  `settingsNamespace`), dsh-context → v0.41.0.
- Resolve the published assemblies' unresolvable devDependencies by dropping
  them in `resolveNpmAssembly()` (the assembly is only consumed by
  `pnpm install --frozen-lockfile` + `deploy --prod`; dev deps never reach
  the staged runtime). The runtime lockfile is generated with every
  `@deepseek-ai/dsh-*` closure member pinned to the line — otherwise pnpm
  resolves `^0.1.2-alpha.3` ranges to the newest prerelease (rc.1 today),
  silently mixing release lines — and the staging shim mirrors the
  lockfile's own recorded overrides verbatim (pnpm rejects a frozen install
  whose recorded overrides differ from current config). The generation
  script lives in the upgrade audit directory.
- The root workspace carries the same line-pinning overrides for the TUI's
  wide union ranges (`^0.1.0-rc.6 || ^0.1.1-rc.1 || ^0.1.2-alpha.2`),
  mirroring the override block the upstream dsh-TUI workspace itself
  carries; pnpm cannot resolve those unions on the 0.1.2 line otherwise.
- Adapt the client contracts at their narrow seams: every `dsh.client.inject`
  list drops `@deepseek-ai/dsh-client-runtime`; skins/sidebar/desktop-frame
  import `defineStore` from `@deepseek-ai/dsh-client-store` (resolved by the
  shell static table, exactly how upstream's own client bundles require it);
  desktop-frame wraps the strict session-scoped `details` outlet in the
  standard `SessionProvider` share; the settings namespace boundary patch
  re-anchors on `dsh-api-settings-controller` (same allowlist semantics);
  both smokes exchange the launch token for a session cookie and retry
  transport-failed requests once (the 0.1.2 server closes idle keep-alive
  sockets and undici does not replay non-idempotent requests); the
  smoke-client composer selectors follow the 0.1.2 DOM (the hero workspace
  picker is a `role=textbox` div, the composer input a contenteditable div
  with `data-phase`).
- The 0.1.2 loader never activates a nested dynamic `ctx.inject` created
  inside another inject's callback. skins and plugin-marketplace therefore
  register sibling FIRST-LEVEL injects per carrier (surface+webServer for
  browser surfaces, surface-only for the TUI palette, surface+commands for
  the TUI slash command), with deliberately empty module-level `inject`
  arrays — the dsh-auth pattern that keeps a stale patch from deadlocking a
  newer boot.
- Remove the built-in `@oh-dsh/vision` bridge plugin: DeepSeek V4 Flash is
  natively multimodal, DSH's native attachment rail (paste, thumbnails,
  submission) is model-agnostic, and the bridge existed to describe images
  for text-only models. The smoke's pasted-image probe stays — it asserts
  the native attachment flow (renamed vision→attachment), which matters
  more now, not less.
- Floating chrome (pinned summary, marketplace surface) anchors inside one
  shared chrome layer (`plugins/shared/chrome-layer.ts`) that spans the
  content region and absorbs the titlebar reservation once; the panels use
  plain absolute corner offsets instead of each re-deriving viewport
  coordinates from `--oh-dsh-titlebar-height`. Modal dialogs demote the
  layer (its panels share its stacking context), replacing the per-panel
  demotion entries.

## Consequences

- All three surfaces ride one coherent 0.1.2-alpha.3 tree (557 resolved
  packages, frozen install). Verified: typecheck, 297 unit tests, frozen
  staging, the desktop and web smoke lanes (client graph, native image
  attachment, skins preferences persistence, marketplace snapshot, sidebar
  Files/Git API, PTY terminal execution), and the TUI launcher help.
- rc.1/alpha.4/alpha.5 remain blocked on dsh-TUI's Session-projection
  adaptation; taking them later is a pin bump plus the lockfile regeneration
  procedure recorded above.
- Nix source pins (revs and npm tarball hashes) are updated, but the four
  fetchFromGitHub nar hashes and both fetchPnpmDeps hashes still carry the
  0.1.1-rc.2-era values — this workspace has no nix runner, so they must be
  refreshed from an actual `nix build` on a nix-capable host (mismatch
  errors print the new hashes). Noted beside the pins in `nix/oh-dsh.nix`.
- npm `@deepseek-harness-tui/dsh-auth@0.1.0` (the Nix release artifact) is
  the 2026-08-24 fba02bc build; the nested beta.4 gitlink 4e7cba3 is
  unpublished, so staged runtimes and Nix assemblies carry different dsh-auth
  builds until upstream publishes.
- The web-server token exchange means every external client of a running
  Oh-DSH web surface must complete the cookie mint before any API call.

## Alternatives considered

**Pin rc.1 (the newest release).** Rejected: no released dsh-TUI runs on it
(`Session.events` is gone); adapting ~50 renderer call sites would mean
editing the pinned submodule, which the pinned-source rule forbids.

**Pin alpha.2 (the TUI's declared validated line).** Rejected: uninstallable
as published (unpublished `dsh-experimental-*` devDependencies).

**Keep 0.1.1-rc.2 and only bump the plugins.** Rejected: every 0.1.2-line
plugin release peers on the 0.1.2 runtime; the surfaces and the runtime
would split exactly as the 0.1.1-rc.2 note warned.

**Keep the vision bridge beside native multimodal.** Rejected: with V4
Flash consuming images directly the bridge adds a second describe path and a
mandatory Zhipu key for no capability gain; removal also drops its settings
namespace and credential handling entirely.
